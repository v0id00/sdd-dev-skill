# Author one spec from an idea

Turn a request or idea into a single complete spec file with `Status: Draft`, ready for the sdd-interview and sdd-review flow. One concern per file; no implementation happens here.

## When to use

- The user brings a new feature, change or bugfix and no spec exists for it.
- A request is too large for one spec and needs a split decision before writing.
- `specs/` exists and the next sequential id must be allocated.
- Decisions from an interview round must be written into the spec.
- A `Draft` spec is half-written and must be completed before approval is requested.

## Inputs

- `specs/README.md` — read it first for the format contract. If `specs/` does not exist, run `sdd init` (sdd-init) first.
- The raw request in the user's own words, and who it is for.
- Existing specs (`specs/INDEX.md`, `sdd list`) so the new one cites instead of duplicates.
- The project's real interfaces, file paths, data model and terminology — read the code, do not invent names.
- Any prior interview round answers to apply.

## Procedure

1. Restate the request in one paragraph: which problem, for whom, what "done" means. Ask the user to correct it before writing.
2. Decide one spec versus several. If several, produce the split list with a one-line purpose each and confirm it.
3. Run `sdd new "<title>"` to allocate the next id and scaffold from the template. Hand-write from `references/spec-template.md` (next to this skill) only when the CLI is unavailable.
4. Keep `- **Status:** Draft`. Fill `Owner`, `Created`, `Updated`. Add `Supersedes` / `Superseded by` / `Rejected reason` only when they apply.
5. Fill every section: `## Purpose`, `## Out of Scope` (explicit non-goals), `## Behavior` (numbered rules plus edge cases and failure modes), `## Interfaces` (exact names, paths, signatures, endpoints — cite other specs instead of copying their tables), `## Data Model` (`n/a` when none), `## Acceptance Criteria`, `## Open Questions`, `## Decision Log`, `## References`.
6. Write 3-8 acceptance criteria as `- [ ] ACn: <observable statement>`, each independently testable by a command, a test run, or visible behavior. Ban "it works" and "looks good".
7. Give every Open Question a blocking yes/no flag. If a blocking question has no answer yet, say so instead of writing vague prose.
8. Self-review against `specs/README.md`: required sections present (`## Purpose`, `## Acceptance Criteria`), filename number equals the `# NNNN — Title` heading, slug lowercase-hyphen, id not duplicated.
9. Run `sdd lint --verbose` until clean, then `sdd index`.
10. Hand off: recommend sdd-interview for the decision rounds and sdd-review for approval. As author, never request approval on your own behalf as if it were granted.

## Outputs

- One spec file `specs/NNNN-slug.md` with `- **Status:** Draft`.
- `specs/INDEX.md` regenerated by `sdd index`.
- Open Questions with blocking flags, and a Decision Log row for each decision already made.

## Guardrails

- Status stays `Draft`. Never self-approve; only the user moves `Draft → Approved`.
- No implementation code here — a `Draft` spec buys no code.
- Do not copy another spec's contract; cite it by id (one contract, one file).
- If the request is too vague to yield a single testable acceptance criterion, stop and ask. Do not pad the spec with vague prose.
- Never reuse an id or renumber an existing spec. Retirement is `Status: Superseded` plus a `Superseded by:` link, never deletion.
- Behavior change means the spec is edited first, in the same commit as the code — not afterwards.

## Verify

- `sdd lint --verbose` — zero errors; fix every warning or state to the user why it stands.
- `sdd stats --json` — the new spec appears as `Draft` with the expected AC total.
- Confirm the filename id matches the heading, e.g. `specs/0007-retry-budget.md` begins `# 0007 — Retry budget`.
- Re-read the Acceptance Criteria and name, for each, the command/test/behavior that proves it — fabricated evidence is banned.
