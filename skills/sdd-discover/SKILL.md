# Reverse-engineer existing behavior into draft specs

Document what the code DOES today, never what it should do. Output is a set of `specs/NNNN-*.md` files with `Status: Draft` plus an honest gap list. It is the starting point for later change, not a redesign.

## When to use

- A codebase has no specs, or only skeleton drafts left by sdd-init.
- The user says "document what this actually does", "write specs from the code", "onboard this legacy repo".
- A module is about to be refactored or replaced and its current behavior is undocumented.
- Immediately after sdd-init in a non-empty repository.
- Specs and code disagree and the as-is behavior must be pinned down first.

## Inputs

- `specs/README.md` present and read first — the format contract. If `specs/` does not exist, run `sdd init` (sdd-init) first.
- The repository at a known state; record the commit hash being described.
- Read access to entry points, routes, CLI commands, handlers, data model and config.
- A scope decision from the user: which surfaces are in v1, which are out.
- Confirmation budget: ONE round of at most five grouped questions, recommendation first.

## Procedure

1. Read `specs/README.md`, then inventory surfaces from the code: entry points, routes/endpoints, CLI commands, scheduled jobs and workers, data model (tables, migrations), external integrations, config and feature flags. Record the file paths as evidence.
2. Group surfaces into spec-sized units — one concern per spec. Prefer 5-15 specs over 40 micro-specs. Name each unit.
3. Confirm the unit list with the user in ONE round of at most five grouped questions, recommendation first, and ask which areas are explicitly out of scope for v1.
4. Allocate ids sequentially with `sdd new "<title>"` — one command per spec, so numbering stays contiguous and ids are never reused.
5. Fill each spec from the code, section by section: `## Purpose`, `## Out of Scope`, `## Behavior` (rules plus edge cases and failure modes read out of the implementation), `## Interfaces` (exact file paths, signatures, endpoints, table columns), `## Data Model`, `## Acceptance Criteria`, `## Open Questions`, `## Decision Log`.
6. Write acceptance criteria as `- [ ] ACn: <observable statement>` describing CURRENT behavior, each provable by running a command, calling an endpoint, or running a test.
7. Mark anything ambiguous, undocumented, or clearly buggy as an Open Question — never as an intended rule.
8. Run `sdd lint --verbose`, fix the findings, run `sdd index`, then `sdd stats` and report the counts.

## Outputs

- `specs/NNNN-slug.md` — one `Draft` spec per surface group, header `- **Status:** Draft`.
- `specs/INDEX.md` — regenerated by `sdd index`.
- Open Questions per spec, plus the explicit in/out-of-scope list.
- `TODO.md` entries for behavior that is broken, risky, or needs a product decision.

## Guardrails

- As-is only. Never describe desired behavior; never propose a redesign inside a discovery spec.
- Do not touch code, config, dependencies or tests. The only files this skill writes are `specs/*.md`, `specs/INDEX.md` and `TODO.md`.
- Every behavioral claim must trace to a file (and line) you actually read. No inference from names alone.
- Uncertain or contradictory behavior becomes an Open Question, never an invented rule.
- Status stays `Draft`. `Draft → Approved` is the user's decision — never self-approve.
- One contract, one file: cite a spec, never copy another spec's table or signature.
- Retire nothing by deletion; a replaced spec is marked `Superseded` with a `Superseded by:` link.

## Verify

- `sdd lint --verbose` — zero errors; every remaining warning is either fixed or explicitly justified to the user.
- `sdd stats --json` — each new spec appears as `Draft` with an AC total.
- Spot-check three specs: re-open the cited file/line and confirm `## Behavior` matches the code.
- Confirm each AC is provable by a named command/endpoint/test; rewrite any that only assert "works".
- `sdd index --dry-run` reports `INDEX.md already up to date`.
