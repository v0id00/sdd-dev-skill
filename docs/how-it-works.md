# How it works

## The one rule everything else follows from

**`specs/` is the source of truth.** Not the code, not the README, not the agent's memory of the last conversation. When code and spec disagree, the spec is what the system is *supposed* to do, and the disagreement is a defect in one of them — worth a decision, never a silent fix.

Everything else in this library is a mechanism for keeping that rule true:

| Failure mode | Mechanism |
|---|---|
| Agent codes first, documents later | `sdd-apply` refuses anything not `Approved` |
| Agent approves its own spec | Status flips to `Approved`/`Rejected` are user-only, stated in every skill that touches status |
| Specs rot into prose | Acceptance criteria must be `- [ ] ACn:` checkboxes, and `sdd lint` counts them |
| "It works on my machine" | `sdd-verify` requires quoted command output; unverified claims are labelled unverified |
| A decision invalidates three other files | The cascade step in `sdd-interview` / `sdd-update`, plus the `cascade-leak` lint rule |
| Someone deletes the awkward spec | Retirement is `Superseded` + a link; the linter flags a `Superseded` spec with no replacement link |
| The index lies | `INDEX.md` is generated by `sdd index`; `lint` reports drift |

## The spec format is a contract, not a style

`sdd lint`, `sdd stats` and `sdd index` parse the header and the sections. That is deliberate: a format the tooling can read is a format that can be *checked*. The minimum a spec must carry:

```markdown
# 0007 — Retry budget

- **Status:** Draft          # Draft | Approved | Implemented | Rejected | Superseded
- **Owner:** unassigned
- **Created:** 2026-09-21
- **Updated:** 2026-09-21
- **Supersedes:** 0003       # optional, links the spec this one replaces
- **Superseded by:** 0011    # required when Status is Superseded
- **Rejected reason:** ...   # required when Status is Rejected
```

File name `NNNN-slug.md`, 4-digit zero-padded, sequential, never reused, and the number must match the heading. Ids are cheap; traceability is not.

## The loop, and why the order matters

```
1 init        make the repo spec-first (or retrofit it)
2 discover    existing code  -> Draft specs describing today's behavior
  spec        new work       -> Draft spec describing intended behavior
3 interview   ask until nothing important is ambiguous (rounds of <=5)
4 review      approve / approve-with-changes / keep draft / reject   <- user decides
5 plan        Approved spec -> tasks, each traced to AC ids
6 apply       implement, AC by AC, verification command after each
7 verify      real evidence per AC -> tick -> Implemented
   status     counts, stale specs, next action (any time)
   lint       format, ids, refs, cascade leaks, staleness (any time)
```

Steps 3 and 4 are where the value is. A spec that reaches `Approved` without a question round is usually a spec full of the author's assumptions wearing a confident tone.

## Interview rounds: ≤5 decisions, recommendation first

Asking "any questions?" produces nothing. The protocol in `sdd-interview` is the opposite — it enumerates every silent assumption the spec makes (defaults, thresholds, storage, error paths, permissions, concurrency, migration, backwards compatibility, observability, cost) and presents them as decidable items:

```
A. Retry budget storage
   A1. in-memory per client instance   <-- recommended
   A2. shared in Redis
   A3. persisted per account
   > A1 is the smallest change that satisfies AC3 and adds no new dependency.

B. What happens on budget exhaustion        <-- critical, needs your call
   B1. raise a typed error and let the caller decide
   B2. fall back to the cached value
```

The user answers a whole round in one line: `A1, B2, and for B: typed error`. Shortcuts: `default` takes the recommendation, `you decide` makes the agent choose **and record the reasoning** in the Decision Log.

### The cascade problem

Decisions leak. In a real project, the decision *"no `.env` file, secrets live in the global config"* invalidated three other files: a section of spec 0001, an acceptance criterion of spec 0002, and a conventions line in `AGENTS.md`. All three had to change in the same pass, or the specs would have contradicted each other while all looking approved.

So each round ends with a cascade step, not a courtesy grep:

```bash
rg "<the phrase or identifier the decision invalidated>" specs/ AGENTS.md CLAUDE.md docs/
sdd lint --verbose      # cascade-leak, broken-ref, index-stale
sdd index               # the index is generated, keep it truthful
```

A companion plan or template that now disagrees must either be updated or carry a visible `SPEC OVERRIDE` note citing the owning spec. A silently stale plan is worse than no plan: it produces code that no longer compiles or quietly diverges.

## Discover is as-is, not as-should-be

Retrofitting specs onto an existing codebase fails when the specs describe the desired system. `sdd-discover` writes what the code **does today**, including:

- behavior read out of the implementation, with the file that proves it,
- edge cases and failure modes the code actually has,
- anything ambiguous, inconsistent or clearly buggy as an **Open Question** — never documented as intent.

That first draft is not approval-worthy, and the skill doesn't pretend it is. Its output is a map of the current system plus an honest list of where the map is blurry, which is exactly what a later decision round needs.

## Multi-agent and multi-tool notes

- Each skill is self-contained, so an agent can load one without the others — that is why the status model and the hard rules are repeated in every skill rather than living in one "read this first" file.
- Project-local installs (`--project`) let a repo carry its own copies; `--global` shares one copy across projects. `--link` symlinks the skills back to the library so edits are live while developing.
- Agents that can only read rules (a `rules` file, an `AGENTS.md`) still get value: `AGENTS.md` repeats the hard rules, and the CLI enforces the mechanical parts regardless of who wrote the spec.
- The CLI is deterministic and agent-independent, which is the point: **numbers and findings come from `sdd`, not from an agent counting files by eye.**

## What this deliberately does not do

- It does not generate code from specs, and it does not verify specs against code automatically. Verification is a real command run at a real moment, by a human or an agent, with output quoted.
- It does not impose a template on your specs beyond the parsed header and two required sections. Everything else (`Behavior`, `Interfaces`, `Data Model`, …) is expected and lint-warned, not enforced.
- It does not store state in a database. Specs are markdown files in your repo; they diff, they review, they survive a vendor switch.
